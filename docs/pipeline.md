# Pipeline

## The agent pipeline

Every task goes through two phases, each bounded by the same iteration limit, unless the project sets the stages its run goes through, which runtime takes each of the run's roles, or how many plan reviews a plan takes (see [Planning is a stage a project can switch off](#planning-is-a-stage-a-project-can-switch-off), [Who reviews a task](#who-reviews-a-task) and [The plan-review budget](#the-plan-review-budget)). The run's roles are the planner, the plan reviewer, the implementer and the reviewer.

The plan phase runs first: the planner explores the codebase and returns a plan as its answer, and the run writes it as the plan file. The plan reviewer checks it and returns its review as its answer; the run writes it to `.ai-factory/plan-reviews/` — ending with `PLAN_REVIEW_PASS`, or a description of the problems. If the plan does not pass, the planner receives the review in its message and returns a revised plan, which the run writes. The cycle repeats up to the plan-review budget ([The plan-review budget](#the-plan-review-budget)). [The reviewers' strictness is intended](concepts/non-convergence.md#the-reviewers-strictness-is-intended).

Once the plan is approved, the implement phase begins: the implementer writes code in the run's working tree and returns its answer, and the reviewer reviews the changes and returns its review, which the run writes to `.ai-factory/reviews/`. If problems are found, the review goes inline into the implementer's next message; it applies fixes, and review repeats. The limit is the same, `max_iterations`. Exhausting the limit in either phase without a PASS signal is a task failure (see [outcomes.md](concepts/outcomes.md)). [The reviewers' strictness is intended](concepts/non-convergence.md#the-reviewers-strictness-is-intended).

## Who reviews a task

Who reviews a task is the runtime of the reviewer role, chosen once where the run is assembled and never a branch inside the flow. The verify step takes one of two kinds: the review, by the reviewer role, or the real test run of test mode, whatever the roles say ([test-mode.md](features/test-mode.md)). The reviewer is by default the run's own: a session on the run's runtime of its own, never the planner's, whether or not a planner ran before it ([Agent sessions](#agent-sessions)). A project may name another runtime for the reviewer role through its [per-project overlay](reference/configuration.md#per-project-overlay): a Hermes instance (Hermes takes any role inside the run) or a head by its folder address (A head takes a role of the run). At its start the run prints each of the run's roles with its runtime, after the agent lines, so who reviews a task shows as the reviewer's line, and then the stages ([Settings keys](reference/configuration.md#settings-keys)).

The run does not close a task at the implementer's turn: a verification always follows it, the review in implement mode and the test run in test mode ([test-mode.md](features/test-mode.md)). In implement mode the reviewer receives the implementer's answer and the previous review in its message, reaches the changes as [Invoking a role](features/agent-runtime.md#invoking-a-role) states, and reviews under the run's reviewer prompt. The run writes the review of iteration N under `.ai-factory/reviews/`, in the grammar of any review: `REVIEW_PASS` on its last line, or its findings, with its remarks for elsewhere under `## Deferred observations`, as the review grammar has it. A pass closes the task: the roadmap task marked done with its duration, the record closed and the change committed. Findings send the implementer to iteration N+1 in its session, within `max_iterations`, the review inline in its message. A task is therefore never closed before its verification, and a finding before closure is the run's own loop, never a new roadmap line. After closure only deferred observations and external reviews remain, disposed at the phase's closure as tasks of their own, and a task that is done is not entered again. A run that stops, or a task shown wrong in its spec or its phase, is repaired through a rescue, `task-rescue`.

No check precedes the review. An implementer's turn that changed nothing reaches the reviewer with an empty diff, and a task whose result already holds is passed by it. A plan review spent without a pass is a failure, and a failure is repaired at the stop by fixing the task's spec or plan and running it again. Under planning off the spec is the plan, laid once, so a fixed spec reaches the run only when the record is rolled back to `planning:1`, which lays it again. The line the run prints when a verification passes or fails names the artifact the kind wrote or read, the review file or the test run's output. Escalation, faults, usage limits and the stop marker act as in the full flow.

## The plan-review budget

The plan review is chosen where the run is assembled, like every other difference of a run, and the flow never asks whether it is off. Where `plan_review_iterations` is set, it is the number of plan reviews a plan gets, in place of `max_iterations`: after a review that fails the planner revises the plan and the revised plan is reviewed again, until a review passes or the number is spent, and then the task stops. At `0` there is no plan review: the planner's plan goes straight to the implementer, the plan reviewer is never called and no plan-review file is written.

The plan-review budget and who reviews a task are independent: with plan review off and the run's reviewer reviewing, the planner's plan goes to the implementer and its code is still reviewed. With planning off no plan exists to review, so the budget does not apply. A project sets them through its [per-project overlay](reference/configuration.md#per-project-overlay); a project that sets nothing runs the full flow described above. An interrupted run resumes in a shortened flow with no step tokens of its own, as [Resume](features/resume.md#step-values) states.

## Planning is a stage a project can switch off

A project sets the stages its run goes through, chosen where the run is assembled and never a branch inside the flow. Planning is one of them, set by `planning` ([Settings keys](reference/configuration.md#settings-keys)). With planning on, the planner plans and the plan reviewer reviews as above.

With planning off the run lays the task's spec, verbatim, at the plan's path under the roadmap's artifact segment, as a `# Plan: <task title>` heading followed by the spec. The spec is found by the contract line's `Spec:` tag, and a task without the tag halts the run; the contract line never stands in for it. No contract line is laid, since the implementer's message points at the roadmap line. The planner and the plan reviewer are never called, and are not resolved, usage-checked or recorded among the run's roles; no plan-review file is written and `plan_review_iterations` has no effect. The record passes through `planning:1` to `planned:1` as a planner's round does, so a crash between the laying and the record repeats the laying.

The implementer receives the task as decomposition wrote it. Its instructions read a plan of either shape, a checklist's unchecked tasks in order or a spec's sections in the order they give, so no variant exists and nothing is chosen at assembly; `DEVIATION:` notes are still reported in its answer, which reaches the reviewer.

The code is reviewed as it is with planning on, by the reviewer role: where the reviewer is a session of the run's own, it is fresh per task and continues across that task's fix iterations ([Agent sessions](#agent-sessions)), and is never carried from one task to the next by [phase sessions](features/phase-sessions.md).

A task's spec carries everything the run must read. Test mode keeps its planner ([test-mode.md](features/test-mode.md)). The switch governs a new record's planning. A record at `planning:1` is planned by the stage the run now has, and a record at `planned:1` keeps its plan, which resume reads on disk as it always has. A record whose next plan-family attempt lies past the first, `planning:N` or `planned:N` with N past 1 or `plan_review_failed:N` at any N, has a planner's revision pending or a plan under review, which a run without those stages does not continue: it halts naming `planning` ([Attempt limits](features/resume.md#attempt-limits)), and the task continues from a rollback to `planning:1`, which lays the spec, or with `planning` set to true.

## Agent sessions

The planner never reviews code. The code reviewer is an agent of its own with a session of its own, on every runtime the run starts it on: fresh per task, continued across the task's fix iterations ([Resume](features/resume.md#what-the-sidecar-holds)), and never the planner's session, so it reads the plan from its message and not from the planner's reasoning. Where the reviewer role is taken by a Hermes instance or a head, the session is the one that instance or head keeps, and it may hold more than the task. Its instructions are the reviewer's and the escalation instructions. The implementer also continues its session across the fix cycle, accumulating the context of its own fixes.

Invocation and native instruction delivery live in [Agent runtime](features/agent-runtime.md); native model and effort values live in [Agent defaults](reference/configuration.md#agent-defaults).

The plan reviewer is a separate agent with a clean session on every attempt. This is deliberate: it looks at the plan without the author's own bias, as an independent reviewer.

Interrupted task continuation follows [Resume](features/resume.md): runtime ownership, saved identities, pending planning and pre-call attempt validation are checked before resumed work proceeds.

An agent's turn is the whole of its life. Each agent the run starts as a process, on Claude or Codex, runs as one non-interactive call whose process ends when the agent ends its turn, and nothing wakes it again for pending work. Commands and delegated work complete before that turn ends; the agent does not promise a later wake-up or result. A tool returning a running operation has not completed that work. [Shared execution instructions](features/agent-runtime.md#shared-execution-instructions) govern how the agent continues it within the active invocation. A Hermes instance answers over his API, and a head answers in its own chat turn, which the run waits for (A head takes a role of the run).

The planner's session also persists across a whole roadmap phase — see [phase-sessions.md](features/phase-sessions.md) for the phase boundary, the reset behaviour, and why the default disables carrying it forward.

For Claude, every invocation prints its session ID after the `--- Claude agent (...) ---` line. That identifier locates the session's own file under `~/.claude/projects/` for diagnosis.

## The file protocol

Agents never communicate directly — only through files in the target project's `.ai-factory/`, and the run writes every one of them. Every role returns its result as its last message, and the run writes it: the plan, the plan review, the code review and the implementer's answer of each iteration. The implementer reads the plan, or under planning off the laid spec; the planner receives the plan review in its next message, and the implementer receives the code review in its next. The implementer's result is the project's tree; its answer, with its `DEVIATION:` notes and any `ESCALATION`, goes into a file of the run's, one per iteration beside the reviews, and reaches the reviewer in its message. The orchestrator coordinates the call order and watches for signals (`PLAN_REVIEW_PASS`, `REVIEW_PASS`, `ESCALATION`).

No role writes an artifact and no runtime has its own path to one: whichever agent takes a role, wherever it lives, the role's turn goes in as one self-contained message ([Invoking a role](features/agent-runtime.md#invoking-a-role)) and its result comes out as its answer. A project's `.ai-factory` may lie outside its repository, and the protocol serves it the same way. The run writes its artifacts as UTF-8 and reads them back as UTF-8, whatever the machine's locale.

Artifact directory layout and per-roadmap routing live on [named-roadmaps.md](features/named-roadmaps.md); resume state built on top of this protocol lives on [resume.md](features/resume.md).

## Completion signals

Every agent uses the same protocol: it returns its result as its answer, the run writes it to a file, and a signal stands as the file's last line if all is well — the file is left without one if problems remain. A reader recognizes a signal when it stands as an exact line among the file's last five lines, so stray text an agent leaves after it does not hide it. The plan reviewer's answer ends with `PLAN_REVIEW_PASS`, the reviewer's with `REVIEW_PASS`, and the run reads the signal from its own file. In test mode the test run, which is not an agent, writes `TEST_PASS` as the last line of its output file when the test command exits 0, and a reader recognizes it the same way (see [test-mode.md](features/test-mode.md)). The orchestrator reads the file, counts iterations, and decides whether to continue or to stop and show the last review to the user. An empty answer is not a result without a signal — it is no result at all, and the run halts rather than counting it (see [fault-handling.md](concepts/fault-handling.md)).

Any of the four roles may instead end its answer with `ESCALATION` as the last line — see [escalation.md](features/escalation.md) for what it means and what it requires.

A review may carry a `## Deferred observations` section before the signal line — a non-blocking channel for observations that are verified but deliberately not blocking, outside the task's own scope. This section's presence does not affect PASS/FAIL: the orchestrator still determines the outcome only from the completion signal.
