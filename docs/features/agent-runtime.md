# Agent runtime behavior

## Agent runtime

An **agent runtime** is the execution environment through which an agent carries out turns, including its native tools, instruction delivery, session continuity and process behavior. Claude Code and Codex are agent runtimes that the run starts as local processes; a Hermes instance (Hermes takes any role inside the run) and a head taking a role of the run (A head takes a role of the run) are two more, which the run reaches. The invocation boundary and its adapter implementations live in [ports.py](../../orchestrator/ports.py), [claude_cli.py](../../orchestrator/claude_cli.py) and [codex_cli.py](../../orchestrator/codex_cli.py).

## Invoking a role

A role asks the runtime to carry out its current turn in the target project's working directory. Every call supplies the role's semantic identity, its complete instructions, the current assignment and the explicit session identity to continue when one exists. The runtime receives role identity separately from the instruction text, so native execution policy does not depend on recognizing prose.

The assignment is self-contained, so that no runtime depends on reaching a path in the run's tree. It carries the plan inline, or under planning off the task's spec laid at the plan's path; a reviewing role also receives the implementer's answer and the previous review inline and reaches the changes as the paragraph below states, so that no message carries the diff, code travelling by git and text by message; on a fix iteration the implementer's message carries the review inline after the plan, whatever session the role holds. Every role receives the grammar its answer takes. Where a message names the roadmap, the planner's and the implementer's first message do in their `Roadmap:` line, it names it by its path relative to the project's root, `.ai-factory/roadmaps/<slug>.md (line N)`, which holds in the tree, in the clone of a role off the machine and wherever the project lies; no message carries an absolute path of the run's tree. An agent that runs in the tree may still read what the message names. A role returns its result as its last message, and the run writes it as the role's artifact ([The file protocol](../pipeline.md#the-file-protocol)); no role writes an artifact.

After the implementer's turn the run puts the iteration's state on a ref of its own as a commit and pushes it, in each repository of the run's tree ([Git repository](../reference/target-project.md#git-repository) states the tree), so that what lies in the folder `.ai-factory` resolves to reaches a role off the machine as the rest of the project does. The commit takes its author and committer dates from that repository's base commit, so it depends only on its tree, its base and its message, and making it again gives the same commit. A message that names the changes names each repository of the tree by what it is, the project's and the one holding `.ai-factory` with the folder's path inside it, and always every one, changed or not; where `.ai-factory` lies in the project's repository the tree is that one and the message names it alone. The message to every reviewing role gives, for each repository, its base and its iteration's commit, and every reviewing role reads the changes as the difference between each pair, whatever runtime takes it and wherever it lives. Every reviewing role reads an iteration with `git show` or `git diff` of the commits its message names, or in a worktree of its own, and never moves the run's HEAD: no commit or branch is checked out in the run's tree, because a checkout of the iteration's commit and back deletes what the run holds only in the working tree. The review's message and the reviewer's instructions both state it. The message to a role that does not review gives each repository's base. The implementer's result reaches the run the same way, as a commit in each repository of the tree. The ref, and the branch an implementer pushes where its runtime pushes one, are named by the roadmap's artifact segment and the task's stem, and in the other repository by the project's folder before them, so that two roadmaps whose tasks share a stem, and two projects in one repository, never share one, and the iteration's ref lies in a namespace of its own, so that no ref of the run shares a short name with the implementer's branch ([Git repository](../reference/target-project.md#git-repository) names them). The run removes its refs in each repository when the task ends, so that the task's branch carries one commit.

The complete instructions remain available on resumed calls as well as new ones. A role's instructions are its own and its escalation instructions together, and the planner's never include code review; changing the turn's assignment does not discard part of them. The adapter chooses how the native runtime receives these instructions. Availability at the boundary does not require appending their full text to the conversation on every turn.

## Shared execution instructions

Every role executed by a model receives common execution instructions alongside its role instructions. The available local capabilities support reading files, enumerating paths, searching contents, editing files and running shell commands. Planners and reviewers return their results as answers. Instructions describe executable actions through the runtime's available tools rather than provider-specific tool names. Each role's instructions are composed once: the common execution instructions, then the role's fragments, then the escalation instructions. The planner's fragment is the planner prompt, or the test planner's in test mode; the plan reviewer's and the code reviewer's are the reviewer prompt; the implementer's is the implementer prompt. Composition ownership lives in [agents.py](../../orchestrator/agents.py).

The agent retains any running cell or session identifier returned by a tool and uses the available continuation or wait operation until terminal completion. It inspects exit status and output before claiming completion. Commands and delegated work follow [the current turn's lifetime](../pipeline.md#agent-sessions).

Role instructions preserve mandatory project-context walks, full-file reads and the obligations of the role's answer. Re-review reopens current files, quotes the current content relevant to each earlier finding and records a verdict for each finding. Review substance, [completion signals](../pipeline.md#completion-signals) and [escalation](escalation.md) retain their requirements.

Structural updates follow the target project's governing documentation homes. The module map belongs in its architecture document where present; AGENTS.md and CLAUDE.md retain their established routing and symlink arrangement.

Foreground completion is an instruction contract. Native settings govern local execution policy; they do not establish a universal absence of background-capable tools, an operating-system security boundary or unattended access to every plugin. Native option values remain in [Agent defaults](../reference/configuration.md#agent-defaults) and [Codex invocation forms](../reference/codex-runtime.md#invocation-forms).

## Execution validation

Offline validation captures the instructions supplied to a fake runtime backend on initial and continuing calls, observing the full composition, the common execution fragment exactly once and current-file reading obligations in re-review assignments. Native argument policy retains its existing coverage against the [invocation reference](../reference/codex-runtime.md#invocation-forms).

Production capability evidence comes from a disposable full pipeline passage with normal project guidance, configuration and authentication. It starts with fresh native threads created with the new complete instructions, then validates continuations within that same initial policy; existing threads cannot hot reload changed instruction text. The target guidance carries a checkable canary, a role's answer is written by the run at an artifact destination that resolves through a real symlink, and a finite command completes before the dependent answer, PASS signal and final response. If a tool yields, its continuation reaches terminal completion within that invocation.

The retained evidence establishes the exercised working directory, guidance use, answer capture, artifact writes and command completion. Its scope is the exercised configuration and tools; it does not establish universal background-tool exclusion. This witness accompanies the full pipeline acceptance passage rather than a separate capability-only pair of model calls.

## Runtime selection

The merged [configuration](../reference/configuration.md#settings-keys) selects the run's runtime once, the default for every role, and a role may name another ([A role's runtime](../reference/configuration.md#a-roles-runtime)). The selection is visible in the run's output; choosing Codex, Hermes or a head is explicit opt-in. A role's model and effort on Claude or Codex come from its own entry in its own runtime's block of the [agent settings](../reference/configuration.md#agent-defaults), and at the start of a run, under the runtime line, the run prints every role with its runtime and, as the role has them, its model and effort, its instance or its address, so they show in the console and in `run.log`. Implement and test runs use the same selection behavior, while test verification follows [Test mode](test-mode.md).

Continuing existing task history requires [Resume prerequisites](resume.md#resume-prerequisites); selecting a runtime does not transfer another runtime's sessions.

A recognized selector is distinct from an available runtime. A runtime that a role takes and that is unavailable surfaces an invocation error before usage probing, the task loop or task-artifact mutation; the run does not substitute another runtime. A local adapter validates its executable during assembly, before those operations, with a missing executable following [Fault handling](../concepts/fault-handling.md#the-known-faults).

Explicit Codex selection runs the shared CLI pipeline. Each taken local runtime's pre-task policy follows [Usage limits](usage-limits.md#selected-pre-task-check), including Codex's read-only account-window check; Claude retains its execution behavior. Construction ownership lives in [main.py](../../orchestrator/main.py).

Disposable full-pipeline validation under [Execution validation](#execution-validation) precedes real Codex project queues. Execution through fallback subagent role loops does not establish native CLI acceptance.

## Native execution

Claude executes the shared roles through its CLI adapter. The adapter owns native tool policy and its flags; a role's model and effort come from its own entry in the role's runtime's block of the [agent settings](../reference/configuration.md#agent-defaults). It supplies the role instructions as the native system prompt on the initial call and uses the explicit session identity for continuation. Session creation and reuse follow [Pipeline — Agent sessions](../pipeline.md#agent-sessions).

The adapter returns the invocation's output, the role's answer, and session identity, or raises the fault described by [Fault handling](../concepts/fault-handling.md). Artifact verdicts and escalation remain governed by [Pipeline — Completion signals](../pipeline.md#completion-signals) and [Escalation](escalation.md); invocation completion alone does not decide the work's outcome. Usage checks follow [Usage limits](usage-limits.md).

The ownership of the runtime boundary, native adapter and shared child-process control is specified in [ports.py](../../orchestrator/ports.py), [claude_cli.py](../../orchestrator/claude_cli.py), [codex_cli.py](../../orchestrator/codex_cli.py) and [process_control.py](../../orchestrator/process_control.py).

## Codex creation and continuation

Codex uses the shared invocation boundary with its native adapter. Creation delivers the complete role instructions in the developer layer and the current assignment on standard input. A supplied thread continues the same role-instruction composition: native continuation retains the initial developer policy. Each role keeps its own instructions and its escalation instructions throughout its assignments.

The adapter validates supplied continuation syntax under [Codex invocation forms](../reference/codex-runtime.md#invocation-forms) before constructing arguments or starting a child. Same-runtime storage and caller preparation remain governed by [Resume prerequisites](resume.md#resume-prerequisites).

The adapter keeps normal project guidance, user configuration, rules and authentication available. It removes inherited caller identity from the child environment and uses the target project as the child working directory. Exact command forms, encoding and environment names live in [Codex runtime — Invocation forms](../reference/codex-runtime.md#invocation-forms). These are intended invocation policy; production permission and foreground-tool behavior remain subject to execution and acceptance validation under [Runtime selection](#runtime-selection).

## Codex completion and failure evidence

Each invocation is read through process exit. Success requires a successful process, an unambiguous terminal completion and one consistent valid thread identity. A continued thread's emitted identity matches the requested identity. The return text is that last completed agent message, rather than concatenated commentary or tool output, and it is empty when the turn completed with none; the run handles an empty one as any role's empty answer, a halt, as [Fault handling — The known faults](../concepts/fault-handling.md#the-known-faults) states. [Codex runtime — Stream fields](../reference/codex-runtime.md#stream-fields) defines the consumed native fields.

Unknown event kinds are ignored. Malformed JSON, malformed consumed fields, conflicting identities and conflicting terminal outcomes surface as protocol defects. A completed successful invocation ignores stale intermediate errors and stderr warnings; assistant prose and tool output are never fault diagnostics.

For a failed or incomplete invocation, its terminal failure message is primary. Without that message, the last top-level native error supplies the primary diagnostic; without either, the last explicit stderr error record does. The exact record boundary and auxiliary-diagnostic rule live in [Failure recognition](../reference/codex-runtime.md#failure-recognition). An unknown primary failure surfaces rather than being replaced by a convenient transient phrase elsewhere. Missing completion or identity, empty output and nonzero exit alone do not establish transport failure. Native output, stderr and exit status remain available in error reports.

Known exhaustion halts the run. Explicit nontransient causes surface ahead of retryable causes; the precise positive forms and exclusions live in [Codex runtime — Failure recognition](../reference/codex-runtime.md#failure-recognition), under [Fault handling](../concepts/fault-handling.md). These decisions concern failed-invocation evidence; recovered intermediate errors never turn success into a fault. A failed turn does not return a result or advance the sidecar even if a plausible artifact exists. The adapter does not certify such an artifact; restart selection remains flow-owned under [Resume](resume.md). Artifact verdicts remain the roles' and pipeline's responsibility.

## Codex retry continuity

Recognized transient faults receive the bounded attempts and delay in [Retry limits](../reference/codex-runtime.md#retry-limits). A requested identity remains the continuation target. When a fresh attempt emits a valid identity before failing, the next attempt resumes that thread with the unchanged assignment and role policy. Only an original fresh invocation with no known identity can retry fresh. A rejected continuation surfaces its fault; retry exhaustion produces the existing infrastructure-halt outcome.

## Codex child lifetime

The adapter starts the child in its own process session and immediately registers it as the active child. It communicates the assignment through stdin while draining separate stdout and stderr pipes through exit; the native stream is parsed after communication completes. Communication closes stdin without bespoke reader workers. Native executable availability is checked during adapter construction without a model call.

Launch, communication and interruption failures retain the native error while cleaning up and reaping any local child and clearing its active reference. Forced quit uses shared child cleanup; soft stop retains the existing [run behavior](../concepts/fault-handling.md#the-known-faults). Process-control ownership lives in [process_control.py](../../orchestrator/process_control.py).
